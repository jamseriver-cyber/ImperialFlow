# 已知边界与适用方式

V1 是单机、可信入口下的治理基线。它已实现请求校验与状态提交约束；部署和身份可信度由接入方负责。

## 实际已实现

- Python Typed Action、Schema 和角色 Action 白名单。
- 正常 HIGH 生命周期门禁、LOW 的 Intake 直接执行边，以及动态部门交接。
- 文件 / 区段 / 哈希证据校验、当前方案与执行包绑定、VOID 拒用、作者与审查者身份独立性检查。
- Canonical Registry、追加 Evidence / Trace、派生 CURRENT_STATE。
- 排他锁、乐观修订校验、原子 Registry 替换、待完成日志和受限恢复。
- 返工、审查和执行纠正预算；Interrupt 分类；治理 Checkpoint 的独立接受边界。

## 尚未提供的能力

| 边界 | 当前含义 |
| --- | --- |
| OS 角色文件权限隔离 | 共享 shell 仍可直接改文件；Runtime 的完整性校验不是文件访问沙箱 |
| 真实身份认证与客户端签名 | Actor / Invocation 由可信入口提供，不能只靠填写不同 identity 证明独立性 |
| 全证据真实性证明 | 哈希只证明引用内容一致，不能证明用户真的批准或实验真的运行 |
| 自动 Agent 调度 | 路由不会创建、调用、暂停或结束 Codex 聊天 |
| 全过程工具代理 | 不控制业务工具的每一步，也不对任意源码和结果文件自动冻结 |
| 跨文件同时原子提交 | 使用事务日志继续完成；不等于操作系统级全文件同时提交 |
| 通用项目初始化与新任务创建 | 接入方需准备经核对的登记与迁移；当前 CLI 无 init / create-task |
| MEDIUM 简化路线 | 规范允许 PLAN → EXECUTE，当前状态机没有通用跳过 REVIEW 的边 |
| CRITICAL 自动 FINAL REVIEW | 需明确治理合同，本基线不提供自动通用路由 |
| 自动预算提升与 token 计费 | 没有自动追加返工次数、成本结算或模型路由 |

接入生产项目时，不能把 Actor 字段、哈希或 Prompt 当作认证系统。对 Runtime 代码、Registry 和 Trace 都拥有写权限的主体可以改写整套本地记录；有对抗性参与方时，应另建受控存储、可信身份和权限隔离。

## 推荐适用范围

适合人负责关键决定、Agent 分次承担职责的小型工程和科研项目；尤其适合核心方法需要先审查、结果需要有来源、阶段边界需要明确的工作。

先采用角色与任务模板，再针对实际接入方式验证 Runtime。需要多用户不互信、远程身份验证、分布式事务或自动编队时，这个基线不能单独满足需求。

## 历史与当前状态

迁移保持已经确认的历史决定，旧任务头部只作为历史。没有来源的批准不补造，作废记录不删除。治理升级不同时宣告业务执行、验证或验收完成。

参考实现已有可执行治理测试；测试通过证明覆盖用例下的行为，不代表独立安全审计、所有部署环境已验证或业务科学结论成立。
